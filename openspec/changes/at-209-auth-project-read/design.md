# Diseño AT-209: identidad y lectura

## Contrato de entrada y salida

`GET /projects` y `GET /projects/{project_id}` requieren `Authorization: Bearer <Supabase access token>`. Cada elemento devuelve solo `id` UUID, `name`, `revision` entero positivo y `access_role` (`owner|editor|viewer`). La lista usa `limit` de 1 a 100 (20 por defecto) y `cursor` UUID exclusivo; responde `{items: ProjectView[], next_cursor: UUID|null}` con orden ascendente de ID. Cursor final: `null`; lista vacía: 200 `{items: [], next_cursor: null}`; detalle ajeno o inexistente: 404; token ausente, vencido, inválido o de otro emisor: 401; token válido sin admisión: 403; Auth/JWKS o configuración de admisión inválida: 503. UUID mal formado: 422. No incluir contactos, oferta, evidencia ni perfil de usuario en esta respuesta. El OpenAPI generado queda en la rama hasta resolver la coordinación con AT-280.

## Identidad

GitHub es solo el proveedor OAuth de Supabase Auth. FastAPI acepta únicamente el JWT de acceso Supabase. El corte implementado requiere firma asimétrica y emisor/audiencia fijos por entorno, sin valores de proyecto en código. PyJWT 2.15.1 acepta solo `RS256`/`ES256`, exige `kid`, verifica firma, `iss`, `aud`, `exp`, `iat`, `nbf` cuando exista, `role=authenticated` y `sub` UUID; rechaza `is_anonymous=true` o mal tipado. El JWKS se obtiene únicamente del emisor configurado; caché máxima de 600 segundos y cooldown de 30 segundos ante `kid` desconocido. Una clave nueva debe publicarse como reserva al menos 20 minutos antes de activarse, siguiendo la guía Supabase; reiniciar el backend purga la caché local si se requiere. Ante clave desconocida durante cooldown o servicio no disponible sin clave válida, fallar cerrado. La variante HS256 no está habilitada: exige una decisión posterior y validación con Auth `/user`, sin distribuir el secreto compartido. No confiar en email, `user_metadata` ni un `user_id` proporcionado por el cliente para autorización.

## Admisión interactiva y separación del modo público

Después de verificar el JWT, `get_interactive_actor` exige que el `sub` pertenezca a `ESTIMATE_INTERACTIVE_ALLOWED_SUBJECTS`, un arreglo JSON de UUID de Supabase Auth configurado **solo en backend** por el operador. Si falta, la lista es vacía y responde 403; si es inválida, responde 503. Se evalúa en cada petición; un cambio de variable del proceso administrado requiere reinicio/redeploy. Esta allowlist es un gate temporal y administrable para la demo, no reemplaza la membresía por proyecto de AT-208 ni constituye la administración persistente y auditada que requiere AT-209 completo. No basar admisión en email, nombre de GitHub, `user_metadata` o el mero hecho de haber entrado por GitHub. El modo público técnico offline usa una superficie separada y no invoca estas rutas ni comparte su identidad de backend.

## Contrato de inicio de sesión futuro con AT-280

El frontend interactivo deberá usar `supabase.auth.signInWithOAuth({provider: 'github', options: {redirectTo: '<origen-app>/auth/callback', scopes: 'read:user user:email'}})` con cliente configurado para PKCE. La aplicación GitHub enviará su callback a `<origen-Supabase-Auth>/auth/v1/callback`; `redirectTo` apunta a la **ruta del frontend**, registrada como URL exacta en la lista permitida de Supabase (sin comodín en producción). Para local, fijar únicamente orígenes loopback explícitos y usar credenciales OAuth de prueba cuando se autorice; este corte no crea ninguna. El callback Angular recibe `code`, lo intercambia una sola vez con `exchangeCodeForSession(code)` en el mismo navegador/origen que guardó el verificador PKCE, borra el código de la URL y llama la API con el access token Supabase. Errores y 403 muestran acceso denegado sin entrar al producto; no redirigir a un `next` externo. GitHub solo aporta identidad: no solicitar `repo`, `public_repo`, `admin:*` ni tokens para GitHub API; confirmar los permisos efectivos en la pantalla de consentimiento antes del despliegue. Solo la URL y la clave pública de Supabase van al frontend; las claves privadas no. Este callback es un **contrato propuesto**, no una ruta implementada ni probada aquí. Las pruebas locales usan email/password exclusivamente para obtener JWT oficiales descartables; por ello aún falta probar la configuración que restringe el proveedor a GitHub.

## SQL y permisos

AT-208 concede SELECT con RLS a `authenticated` en `projects` y `project_memberships`; la política deja ver propietario o miembro. `at208_backend` no tiene SELECT general ni DML directo. Crear fuera de la migración un LOGIN privado de lectura `NOINHERIT NOBYPASSRLS` con capacidad `SET ROLE authenticated` y sin pertenencia a auxiliares de AT-208. La contraseña reside solo en backend. Cada conexión verifica por `pg_roles` que su LOGIN sea `LOGIN`, `NOSUPERUSER`, `NOBYPASSRLS` y `NOINHERIT`; una conexión demasiado privilegiada falla cerrado con 503. El código abre una conexión por petición y usa `BEGIN READ ONLY ISOLATION LEVEL READ COMMITTED`, `SET LOCAL ROLE authenticated`, `SELECT set_config('request.jwt.claim.sub', <sub verificado>, true)`, una consulta parametrizada que deriva `access_role` del propietario o membresía, `COMMIT`. Ni la cabecera ni el cuerpo controlan SQL, rol o GUC sin verificación. Una futura piscina de conexiones deberá conservar exactamente esta frontera y probar el reinicio del estado. RLS y el filtro explícito por usuario son defensas complementarias. El detalle devuelve 404 si la consulta no produce fila.

Las futuras mutaciones usarán otro LOGIN sin herencia con `SET LOCAL ROLE at208_backend` dentro de una transacción `READ COMMITTED`, `p_actor` del mismo JWT verificado e idempotencia del comando. Ante `40001`/`40P01`, reintentar la transacción completa con límite y la misma clave; no reintentar indiscriminadamente un `23505` de clave incompatible. Probar el modo de pooler elegido con esta secuencia antes de desplegar; este corte no selecciona ni configura pooler. No usar `service_role` como sustituto ni exponer `private` como RPC.

## Pruebas y rollback

Tests unitarios con pares de claves efímeras y JWT sintéticos cubren válido, ausente, caducado, firma/algoritmo/emisor/audiencia/rol no aceptados, rotación y fallo de JWKS. HTTP TestClient usa el verificador real con un JWKS local y PostgreSQL 17 descartable con migración AT-208: propietario, editor, lector y usuario ajeno; paginación acotada, revocación de membresía con el mismo token todavía válido, alternancia de sesiones, 200/401/404/422/503 y sin fuga entre proyectos. Además, GoTrue oficial v2.198.0 y PostgreSQL 17-alpine en contenedores descartables emiten JWT ES256 y JWKS reales; FastAPI los verifica y lee con RLS AT-208. El fixture local solo aporta roles y `auth.uid()` ya presente en GoTrue. No se probó OAuth GitHub, pooler ni aprovisionamiento alojado. Rollback: retirar las rutas y el LOGIN privado de lectura tras verificar que no hay dependencias; no alterar datos de proyecto.

## Coordinación OpenAPI con AT-280

El contrato propuesto está generado en `estimate-api/contracts/openapi.json` y su `--check` local pasa. `estimate-app/develop` mantiene el ancla `APPROVED_SHA=6ecc9a9c5d6ba6355e3332f8b6533c81ed878b74` en `scripts/check-canonical-api.mjs`: exige bytes iguales entre el blob aprobado, `estimate-api/develop` y la copia de app. Además `scripts/generate-contract.mjs` solo acepta `/health`. Fusionar este OpenAPI a API rompería el CI de app. Secuencia segura: (1) fijar la versión y SHA256 exactos de ambos OpenAPI; (2) en AT-280 preparar el generador Angular para las proyecciones tipadas de ambas versiones, con un verificador de una lista cerrada de pares versión/hash aprobados y sin ejecutar contenido del contrato ni aceptar rutas o esquemas desconocidos; (3) aprobar una ventana de transición explícita que permita únicamente el par API nuevo/app anterior mientras el cliente tipado ya soporta ambos, con CI en ambos repositorios; (4) integrar AT-209 y actualizar enseguida el artefacto y ancla de app al SHA fusionado, retirando el par transitorio. Cada estado compara bytes/hash exactos y ancestría del commit aprobado, no deriva arbitraria. Si la compuerta no puede expresar esa ventana sin relajarla, coordinar una integración atómica controlada antes de fusionar API; este worktree no cambia reglas de app ni abre PR. No presentar el cambio como listo para merge mientras ese camino no esté resuelto.

## Corte local de preview HTTP con presupuesto de prueba (27/11/2026)

`POST /v1/projects/{projectId}/scope-review-preview` recibe `{brief}` con 1..4000 caracteres e `Idempotency-Key` (1..100). Devuelve `scope-review-preview.v1` con `projectId`, `state=pending_review`, `requestedQuantity`, `question`, `evidenceIds`, `proposal.status`, `proposal.availableQuantity`, `reviewRequired=true`, `persisted=false` y `commercialReady=false`. El handler requiere JWT, admisión y rol propietario/editor actual. Está deshabilitado por defecto; sin extractor inyectado y DSN de reserva local retorna 503, sin llamar a proveedor. El extractor de pruebas es un stub exclusivo del servidor de prueba, no del backend de producto.

La reserva descartable está en tabla `private` creada solo por `tests/at209/local_preview_reservations.sql`, sin migración alojada. Un LOGIN privado `NOINHERIT NOBYPASSRLS` tiene acceso solo a esa tabla y capacidad de `SET ROLE authenticated` para reconsultar membresía bajo RLS. La transacción usa bloqueo asesor global para serializar recuentos de la última hora (2/actor, 4/proyecto, 8/global) entre procesos, reconsulta propietario/editor dentro de la transacción, rechaza duplicados por clave y confirma una reserva antes del stub. Cualquier error de DB o rol cierra con 503, y cuota agotada con 429. Ninguna reserva contiene el `brief`, tokens o datos comerciales. Este prototipo no autoriza gasto real ni despliegue: una implementación pagada deberá revalidar pertenencia frente a revocación concurrente y definir compensación de reservas fallidas en su frontera transaccional.

El punto de autorización local es la lectura de propietario/editor dentro de la transacción serializada, justo antes de insertar la reserva. El recibo privado pasa de `pending` a `complete` con la respuesta sintética, o `failed` sin respuesta; la clave repetida de un recibo completo devuelve esa respuesta, y `pending`/`failed` responde 409 sin nueva llamada. El cupo sigue contado ante fallos del extractor o del guardado del resultado. No se mantiene transacción ni bloqueo durante el extractor. Una revocación que confirma **después** de esta lectura puede ocurrir antes de la llamada externa; impedir esa carrera en un servicio pagado requiere un protocolo coordinado de autorización/cancelación y no se afirma aquí.

Para vincular la clave al contenido sin cambiar la tabla descartable, el UUID interno del recibo se deriva de los primeros 128 bits de SHA-256 con dominio versionado y campos UTF-8 de longitud explícita: actor, proyecto, clave y brief exacto. La restricción única existente por actor/proyecto/clave recupera el recibo; solo se reproduce si el UUID derivado coincide. Un brief distinto devuelve 409 incluso si el recibo está completo. El hash no es un mecanismo de confidencialidad; solo hay datos sintéticos y la tabla `private` sigue restringida al login de pruebas. La cabecera vacía o formada solo por espacios se rechaza con 422 en HTTP antes de entrar en la reserva.
