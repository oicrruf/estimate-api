# Design

## Context

El `develop` de partida es `c503575e152430908da3f0bb56317867e77d26c9`; se revisó también `846f0e1c2b9eaaee8256794aa5659959b3676022` antes de esta corrección. ADR 0001 elige Supabase PostgreSQL, Auth y Storage; AT-264 fija trece tipos de entidad y paquetes por sujeto. Se leyó la descripción completa de AT-208 en Linear el 26/11/2026. Los comandos de CLI se verifican con `--help` y ninguna operación apunta al proyecto alojado.

Referencias de semántica RLS: [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security) y [PostgreSQL 17 row security](https://www.postgresql.org/docs/17/ddl-rowsecurity.html). En particular, FORCE RLS también somete al propietario normal; un rol con BYPASSRLS lo omite. La prueba local usa propietarios auxiliares sin BYPASSRLS y políticas acotadas.

## Goals / Non-Goals

**Goals:** esquema versionado que haga imposible una relación entre proyectos distintos, guarde historia comercial sin calcular precios y haga cumplir RLS/privilegios bajo identidad autenticada. Probar dos usuarios y dos proyectos en PostgreSQL descartable, incluido backup y restore de ensayo.

**Non-Goals:** validar JWT, configurar Supabase Auth o Storage alojados, exponer API de producción, importar catálogo real, calcular tarifas/impuestos o desplegar. AT-209 se encarga de la autenticación del servicio; AT-224 es propietario de la política de precios.

## Decisions

1. **Identidad de tenant.** `projects` tiene `id` UUID y `owner_user_id` que referencia `auth.users`. La propiedad no se actualiza mediante UPDATE directo de usuario. `project_memberships` contiene solo `editor` o `viewer`, clave `(project_id,user_id)`; el propietario se deriva de `projects`, sin fila duplicada. Una función privada de transferencia exige actor igual al propietario actual y destino miembro editor, bloquea la fila de proyecto, cambia el propietario y convierte al anterior en editor dentro de la misma transacción. Su invocación desde API con JWT verificado pertenece a AT-209.
2. **Core y referencias.** `project_entities` guarda el sobre universal (tipo, etiqueta, origen, ámbito, revisión, estado) y JSON de datos no normativos. `project_relations` y `project_packages` usan claves compuestas `(project_id,entity_id)` para referenciar sujeto y destino del mismo tenant. El catálogo `catalog_items` es global, versionado y de lectura para usuarios autenticados; su escritura queda fuera de privilegios de usuario. No se codifica un rubro en el esquema.
3. **Historia comercial.** `project_offers` es append-only, con proveedor de referencia, moneda, precio observado `numeric(18,4)`, fechas de observación y vigencia; no calcula tasas ni impuestos. `project_budgets` tiene índice único parcial para **como máximo** un presupuesto activo; un proyecto recién creado puede no tener presupuesto hasta que la API lo cree. `budget_lines` usa FKs compuestas a presupuesto y oferta del mismo proyecto. `proposal_snapshots` es append-only y guarda representación JSON versionada de la propuesta; ninguna tabla de historial admite UPDATE/DELETE a roles de usuario.
4. **RLS, propietario y roles.** Todas las tablas `public` nuevas tienen RLS. Los tres auxiliares de lectura pertenecen a `at208_policy_owner` (`NOLOGIN NOBYPASSRLS`) con SELECT en proyectos/membresías y políticas para evitar recursión bajo FORCE RLS. Las funciones mutadoras pertenecen a `at208_mutation_owner` (`NOLOGIN NOBYPASSRLS`) con grants y políticas para las tablas que usa cada función. El trigger de auditoría pertenece a `at208_audit_owner` (`NOLOGIN NOBYPASSRLS`) con INSERT solo en eventos. La conexión `at208_backend` carece de BYPASSRLS y DML directo; recibe EXECUTE solo de funciones nombradas. El migrador local tampoco tiene BYPASSRLS. Los roles y su pertenencia deben preexistir; el SQL falla al inicio si faltan, si un auxiliar tiene LOGIN, si el migrador no tiene capacidad `SET ROLE` hacia cada auxiliar o si un rol de cliente/backend u otro LOGIN ordinario puede asumirlo. Los superusuarios de plataforma quedan fuera de la inspección genérica de LOGIN: PostgreSQL les atribuye pertenencia implícita aun sin GRANT. Solo el `session_user` migrador conectado queda exceptuado entre LOGIN no superusuarios y debe ser confiable. No se usa `service_role` como ruta RPC. El stack alojado y la conexión SQL real no se comprobaron. El contexto de `auth.uid()` solo es confiable tras JWT validado; el harness local lo simula.
5. **Auditoría.** Un trigger privado registra mutaciones de tablas de proyecto con `auth.uid()` y metadatos mínimos. Rechaza actor ausente. La función no copia `facts`, precio ni snapshot al log. Su propietario privilegiado solo escribe en `audit_events`; no se expone como RPC. Pruebas revisan que el evento aparece y que roles de usuario no pueden falsificarlo ni editarlo.
6. **Comandos confiables.** Se retira todo DML directo de `authenticated` y `at208_backend` sobre proyectos, membresías y tablas comerciales. Las funciones privadas nombradas crean proyecto, gestionan membresía, transfieren propiedad, registran declaración de usuario/evidencia curada, asocian paquete curado, registran oferta/tarifa/cliente/candidato/evaluación/selección, y gestionan presupuesto/línea/borrador. Cada una recibe actor que FastAPI deberá derivar de JWT verificado, autoriza por proyecto, bloquea proyecto primero e idempotentemente registra payload y resultado. Oferta/tarifa fijan revisión y contenido de evidencia al insertar; el reintento de oferta usa el recibo anterior aunque la evidencia luego cambie. Línea/transición de presupuesto exigen revisión vigente. El borrador se proyecta desde líneas y antecedentes fijados; no autoriza emisión (AT-222). Los hechos de paquetes se copian de una versión global curada; la política de cálculo queda en AT-224. Mutaciones de evidencia/paquete/catálogo y datos emitidos no tienen ruta de cliente arbitraria.
7. **Integración y reversión.** La migración se crea con la CLI oficial y no se aplica al proyecto alojado. El ensayo local restaura una copia previa en una base descartable; en producción una migración correctiva es preferible a borrar datos. `pg_dump`/`pg_restore` de prueba comprueban esquema y datos sintéticos. No hay tabla de precios calculados ni política duplicada de AT-224.
8. **Entidades comerciales fundacionales.** `countries`, `suppliers` y `supplier_branches` son directorios compartidos de lectura; `supplier_contacts` y perfiles de cliente viven en `private` sin permisos de cliente. `project_customers`, candidatos, evaluaciones y selecciones se vinculan siempre por `project_id` y FKs compuestas. `product_specs`, fuentes, equivalencias verificadas y garantías mantienen la identidad global deduplicada por marca/modelo/SKU aun si un proyecto descarta el candidato. Las ofertas enlazan proveedor/sucursal/fuente y conservan observaciones históricas; las tarifas de servicio son observaciones fechadas, no reglas de cálculo. Una secuencia `evaluation_seq` asignada bajo bloqueo del proyecto determina la última evaluación aun si dos ocurren en la misma transacción. Al rechazar una candidatura elegida, la selección activa pasa a `superseded` y queda como historia; el índice parcial permite solo una selección activa por requisito. Ninguna tabla nueva concede DML directo a `authenticated`, `service_role` o `at208_backend`; las rutas de escritura implementadas se limitan a funciones nombradas de servicio.

## Riesgos / Trade-offs

- [Función `SECURITY DEFINER` puede ampliar permisos] → esquema no expuesto, búsqueda fija, revocación explícita y tests de acceso; revisar en checkpoint de seguridad.
- [Una sesión SQL puede falsificar el GUC de JWT si posee conexión directa] → no conceder conexión directa a usuarios; AT-209 valida JWT y usa contexto de identidad confiable. El harness local no prueba autenticación.
- [Backend privilegiado o actor falsificado] → rol SQL separado sin BYPASS ni DML; solo funciones explícitas. FastAPI/JWT se verifica en AT-209 y el rol/credencial real en stack compatible antes de desplegar.
- [Ofertas/snapshots crecen] → índices por proyecto/fecha y retención posterior; no aplicar borrados automáticos en AT-208.
- [Índice parcial garantiza solo máximo uno activo] → API crea primer presupuesto en transacción y maneja conflicto 23505; no proclamar existencia obligatoria.
- [Restore puede perder datos posteriores al backup] → probar recuperación con fixtures, documentar RPO/RTO antes de producción.
- [Compatibilidad no probada del hosting] → roles NOLOGIN, pertenencia del migrador, pools/conexión SQL y grants deben probarse en Supabase local compatible; PostgreSQL 17 con fixture no demuestra la topología alojada. Mantener PR draft y AT-208 In Progress hasta revisión independiente y CI final.
- [Espacio Docker insuficiente en el ensayo oficial] → el pull de `ghcr.io/supabase/postgres:17.6.1.102` fijado por digest falló al registrar una capa con `no space left on device`; no limpiar imágenes o volúmenes de otros proyectos. Repetir el ensayo en un Docker aislado con capacidad suficiente antes de integrar.

## Migration Plan

1. Validar OpenSpec antes de escribir SQL. Crear migración con `supabase migration new` verificado por `--help`.
2. Aplicar sobre PostgreSQL 17 descartable con roles Supabase y `auth.uid()` simulados **solo en harness local**; ejecutar pruebas de esquema, RLS, FKs, historial y auditoría.
3. Exportar la base sintética y restaurar en otra base descartable; verificar recuentos, restricciones y RLS. Ensayar reversión en copia, no en base alojada.
4. Publicar propuesta para revisión fresca de diseño de RLS, funciones privilegiadas y matriz de acceso; esperar checkpoint antes de integrar. No tocar Supabase alojado.

## Checkpoint de revisión antes de integrar

Revisor independiente debe examinar superficie `public`, cada GRANT y política, funciones privadas privilegiadas, FKs de tenant, protección del propietario, actor de auditoría, test de roles reales y plan de rollback. La aprobación se refiere al diff SQL y resultados reproducibles, no a una afirmación de seguridad de JWT o del proyecto alojado.
