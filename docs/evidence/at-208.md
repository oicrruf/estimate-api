Fecha: 2026-11-26. Base original: `develop` `c503575e152430908da3f0bb56317867e77d26c9`; se inspeccionó el nuevo `develop` `3adf52e2ff71556df1cddc95282a958d3b8e892e` antes de la corrección. El PR contra `develop` ejecuta CI sobre la combinación actual.

## Ejecución reproducible

Desde la raíz del repositorio, con Docker disponible:

```bash
bash tests/at208/run_local.sh
```

El script crea un contenedor `postgres:17-alpine` sin red ni puerto publicado y lo elimina al terminar. Aplica un fixture local de roles y `auth.uid()` simulado. Primero verifica que la migración falle cerrada con propietario sin `BYPASSRLS`; después la aplica con un propietario `NOLOGIN BYPASSRLS` no superusuario y ejecuta pruebas SQL. Exporta la base con `pg_dump -Fc`, restaura otra base con `pg_restore`, comprueba que el usuario B solo ve su proyecto, y restaura después la copia del esquema anterior a la migración. La salida observada fue:

```text
AT-208 domain, service and RLS assertions passed
AT-208 local migration, RLS, backup/restore and baseline rollback passed
```

El test comprueba dos proyectos, cuatro usuarios (propietarios, editor y viewer), rechazo de relaciones/ofertas entre proyectos, un máximo de un presupuesto activo, fechas inválidas, precios/cantidades `NaN` e infinitos rechazados y valores finitos aceptados. Comprueba que usuarios autenticados no pueden escribir directamente entidades, paquetes, ofertas, presupuestos, líneas ni snapshots, y que `service_role` tampoco tiene DML directo; la función privada registra una oferta con actor/editor, evidencia existente, reintento idempotente y una sola revisión adicional. Verifica auditoría, transferencia solo a editor actual y fallo cerrado sin identidad. La restauración prueba legibilidad y un caso de aislamiento; no mide RPO/RTO ni sustituye un simulacro con datos reales.

OpenSpec CLI `@fission-ai/openspec` 2.2.0: `openspec validate at-208-postgres-domain --strict` → `Change 'at-208-postgres-domain' is valid`. El cambio permanece activo porque AT-208 tiene cobertura pendiente.
`uv run --no-sync python scripts/check_secrets.py` → `No potential secrets detected`.
`uv run --no-sync pytest -q` → `61 passed, 1 warning` (deprecación de Starlette/AnyIO).

La migración fue creada con `supabase@3.4.0 migration new at_208_postgres_domain` dentro de un contenedor Node debido a que el CLI local intentó escribir en un home de solo lectura. El fixture `tests/at208/local_auth_fixture.sql` no debe desplegarse: acepta un claim simulado y no valida JWT. La migración requiere los roles y objetos `auth` provistos por Supabase. Antes de aplicarla se debe verificar en el entorno alojado el atributo y propietario reales del rol migrador, los grants efectivos y herencia de `service_role`, exposición del esquema `private` y política de funciones. No se hizo esa verificación ni se aplicó cambio alguno al proyecto alojado.

La función de oferta es una frontera de base de datos, todavía sin ruta FastAPI que demuestre validación de JWT. El `p_actor` solo puede provenir del backend de confianza; una clave de servicio comprometida podría atribuir otro actor. No se probó autenticación real, backup administrado de Supabase, carrera simultánea de transferencia, ni despliegue. La prueba secuencial rechaza un destino degradado de editor a viewer, y la función bloquea y comprueba la fila de membresía al transferir.

Estos modelos y las rutas transaccionales para presupuesto, líneas, entidades, paquetes y snapshots siguen pendientes. El snapshot actual solo representa un borrador inmutable; no autoriza emisión.
