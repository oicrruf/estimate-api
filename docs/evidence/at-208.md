# AT-208: evidencia local y límites

Fecha: 2026-11-26. Base original: `develop` `c503575e152430908da3f0bb56317867e77d26c9`; se inspeccionó `develop` `846f0e1c2b9eaaee8256794aa5659959b3676022` antes de la corrección. El PR contra `develop` ejecuta CI sobre la combinación actual.
Se usaron únicamente identidades, proyectos y ofertas sintéticos. No se conectó al proyecto Supabase alojado.

## Ejecución reproducible

Desde la raíz del repositorio, con Docker disponible:

```bash
bash tests/at208/run_local.sh
```

El script crea un contenedor `postgres:17-alpine` sin red ni puerto publicado y lo elimina al terminar. Aplica un fixture local de roles y `auth.uid()` simulado. Primero verifica que la migración falle cerrada si el migrador no pertenece a los roles requeridos; después la aplica con un migrador `NOLOGIN NOBYPASSRLS` y auxiliares de lectura, mutación y auditoría con propietarios separados `NOLOGIN NOBYPASSRLS`. Exporta con `pg_dump -Fc`, restaura con `pg_restore`, comprueba aislamiento y recuentos de datos, y restaura la copia anterior a la migración. La salida observada fue:

```text
AT-208 domain, service and RLS assertions passed
AT-208 trusted rate and budget assertions passed
AT-208 two-session membership/transfer race passed
AT-208 local migration, RLS, backup/restore and baseline rollback passed
```

El test usa cuatro proyectos y cinco usuarios sintéticos. Cubre FKs entre proyectos, catálogo acumulativo, contactos privados, RLS en toda tabla pública, rechazo de DML directo de cliente/backend, valores no finitos, único presupuesto activo, auditoría y fallo cerrado. La admisión rechaza propietarios auxiliares LOGIN y membresía de `authenticated`, `at208_backend` o un LOGIN no confiable antes de crear objetos de dominio. Ejecuta comandos SQL de proyecto/membresía/transferencia, declaración/evidencia/paquete curado, cliente, oferta/tarifa, candidatura/evaluación/selección y presupuesto/línea/borrador. Comprueba idempotencia, revisión esperada, proyección de borrador y evidencia histórica fijada tras cambiar la entidad fuente. Una evaluación adversa supersede una selección activa sin borrarla; otra evaluación en la misma transacción recibe secuencia mayor y permite una nueva selección. La prueba de dos sesiones degrada un editor mientras una transferencia espera el bloqueo del proyecto; luego rechaza la transferencia. La restauración prueba legibilidad y recuentos; no mide RPO/RTO ni sustituye un simulacro alojado.

## Ensayo con imagen oficial Supabase PostgreSQL

Se intentó `docker pull ghcr.io/supabase/postgres:17.6.1.102@sha256:90c82488dc721a2b6516c1634b2cc000633f972c4eb6100b68c5aef23ee9e275` (imagen oficial PostgreSQL 17.6.1.102, digest Linux amd64). Docker 29.9.2 rechazó el registro de una capa con `failed to register layer: ... no space left on device`. `docker image inspect` confirmó que la imagen no quedó instalada. No se ejecutó la migración en Supabase Postgres ni se limpió globalmente Docker. Para reproducir en un Docker aislado con espacio suficiente: descargar esa imagen, iniciar una instancia sin red externa, aprovisionar los roles auxiliares con un administrador local, aplicar la migración como migrador esperado y ejecutar `tests/at208/domain_rls.sql`, `trusted_budget.sql` y `concurrent_membership.sh`; el fixture actual de `auth.uid()` es solo para PostgreSQL descartable y no debe confundirse con Auth real.

El PR usa un workflow propio en `ubuntu-latest`. En el [run 99](https://github.com/oicrruf/estimate-api/actions/runs/45840080703) la imagen `17.6.1.102` aplicó el preflight y la migración AT-208 bajo `at208_owner`, pero PostgreSQL recibió `signal 11: Segmentation fault` al ejecutar un bloque de lectura/denegación de DML como `authenticated`. No se observó backup/restore en esa imagen. Un [issue de Supabase Postgres](https://github.com/supabase/postgres/issues/2112) atribuye un fallo de la misma clase en imágenes .099–.112 a `supautils` 3.2.0/3.2.1 y documenta la corrección en 3.2.2; esto apoya, sin probar un backtrace idéntico, que .102 era un pin inadecuado.

Se fijó `ghcr.io/supabase/postgres:17.6.1.156@sha256:665efa7e234a3c324718fd2b7fbbaaaf7263f2565bc2e8fce8555c4def4c4985` (Linux amd64). Se verificó el digest con `docker buildx imagetools inspect ghcr.io/supabase/postgres:17.6.1.156`. En [AT-208 database run 2](https://github.com/oicrruf/estimate-api/actions/runs/45841668867) pasaron **AT-208 official Supabase PostgreSQL** y **AT-208 SQL, OpenSpec and recovery**. El script aplicó la migración como `at208_owner`, probó roles/grants/RLS, usuarios y proyectos sintéticos, comandos confiables, pruebas negativas, concurrencia, backup/restore y reversión. En [Estimate API CI run 105](https://github.com/oicrruf/estimate-api/actions/runs/45841668883) todas las fases, incluido `verify`, pasaron. La imagen Postgres oficial con `auth.uid()` simulado no demuestra JWT, conexión de pooler ni servicios Auth/Storage completos; estos límites permanecen abiertos para integración posterior.

El preflight local se revalidó con PostgreSQL 17: un segundo LOGIN SUPERUSER sin GRANT no produce falso positivo; el rol migrador sin capacidad `SET ROLE` se rechaza; `authenticated`, backend y un LOGIN ordinario con acceso al auxiliar también se rechazan. [Documentación PostgreSQL 17: `pg_has_role`](https://www.postgresql.org/docs/17/functions-info.html) y [membresía de roles](https://www.postgresql.org/docs/17/role-membership.html).

OpenSpec CLI `@fission-ai/openspec` 2.2.0: `openspec validate at-208-postgres-domain --strict` → `Change 'at-208-postgres-domain' is valid`. El cambio permanece activo porque AT-208 tiene cobertura pendiente.
`uv run --no-sync python scripts/check_secrets.py` → `No potential secrets detected`.
`uv run --no-sync pytest -q` → `61 passed, 1 warning` (deprecación de Starlette/AnyIO).

La migración fue creada con `supabase@3.4.0 migration new at_208_postgres_domain` dentro de un contenedor Node porque el CLI local intentó escribir en un home de solo lectura. El fixture `tests/at208/local_auth_fixture.sql` no debe desplegarse: acepta un claim simulado y no valida JWT. La migración requiere los objetos `auth` de Supabase y roles `at208_policy_owner`, `at208_mutation_owner`, `at208_audit_owner` (NOLOGIN NOBYPASSRLS) y `at208_backend` (sin BYPASS ni DML), aprovisionados fuera de ella. El migrador debe pertenecer a los tres propietarios. Antes de aplicar se debe probar esa topología, grants efectivos, conexión SQL backend y no exposición de `private` en un stack Supabase local compatible. PostgreSQL con fixture demuestra lógica SQL, no compatibilidad alojada. No se accedió al proyecto alojado.

Los procedimientos SQL aún no tienen ruta FastAPI que demuestre validación de JWT. `p_actor` debe venir del backend tras verificar el token; una credencial backend comprometida podría atribuir otro actor. FastAPI/JWT corresponde a AT-209. Tampoco se probaron respaldo administrado de Supabase, pooler/rol alojado ni despliegue. Los roles mutadores ya no poseen BYPASSRLS en el ensayo local, pero un revisor debe comprobar sus grants, políticas y superficie de funciones antes de integrar.

La descripción completa de AT-208 en Linear exige también revisión e integración. Las rutas SQL anteriores están probadas en PostgreSQL 17 genérico y en la imagen oficial Supabase Postgres fijada; actualización arbitraria de evidencia/hechos, emisión de propuesta y reglas de cálculo siguen deliberadamente cerradas. El snapshot solo es borrador; AT-222 define emisión y AT-224 cálculo. **AT-208 no cumple Done** hasta la revisión independiente, integración y gates de conexión SQL/Auth aplicables. JWT/FastAPI se integra en AT-209.
