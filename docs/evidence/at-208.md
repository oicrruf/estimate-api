# AT-208: evidencia local y límites

Fecha: 2026-11-26. Base original: `develop` `c503575e152430908da3f0bb56317867e77d26c9`; se inspeccionó el nuevo `develop` `3adf52e2ff71556df1cddc95282a958d3b8e892e` antes de la corrección. El PR contra `develop` ejecuta CI sobre la combinación actual.
Se usaron únicamente identidades, proyectos y ofertas sintéticos. No se conectó al proyecto Supabase alojado.

## Ejecución reproducible

Desde la raíz del repositorio, con Docker disponible:

```bash
bash tests/at208/run_local.sh
```

El script crea un contenedor `postgres:17-alpine` sin red ni puerto publicado y lo elimina al terminar. Aplica un fixture local de roles y `auth.uid()` simulado. Primero verifica que la migración falle cerrada con propietario sin `BYPASSRLS`; después la aplica con un migrador `NOLOGIN BYPASSRLS` no superusuario, auxiliares de lectura propiedad de un rol `NOBYPASSRLS`, y ejecuta pruebas SQL. Exporta la base con `pg_dump -Fc`, restaura otra base con `pg_restore`, comprueba que el usuario B solo ve su proyecto y recuentos de productos, candidaturas, selecciones y perfiles privados; después restaura la copia del esquema anterior a la migración. La salida observada fue:

```text
AT-208 domain, service and RLS assertions passed
AT-208 local migration, RLS, backup/restore and baseline rollback passed
```

El test comprueba dos proyectos, cuatro usuarios (propietarios, editor y viewer), rechazo de relaciones/ofertas entre proyectos, un máximo de un presupuesto activo, fechas inválidas, precios/cantidades `NaN` e infinitos rechazados y valores finitos aceptados. Comprueba directorios de país/proveedor/sucursal, deduplicación de producto por marca/modelo/SKU, especificación/fuente/garantía, clientes y contactos privados, candidatos rechazados conservando el producto global, evaluación/selección con FKs del mismo proyecto, y tarifa de servicio histórica. Todas las tablas públicas tienen RLS. Los usuarios autenticados no pueden escribir directamente dominio/comercio, `service_role` no puede invocar las funciones privadas, y el rol SQL `at208_backend` sin BYPASS ni DML directo ejecuta oferta, candidatura, evaluación y selección con actor/editor, evidencia existente, reintentos idempotentes y revisión atómica. Verifica auditoría, transferencia solo a editor actual y fallo cerrado sin identidad. La restauración prueba legibilidad y un caso de aislamiento; no mide RPO/RTO ni sustituye un simulacro con datos reales.

OpenSpec CLI `@fission-ai/openspec` 2.2.0: `openspec validate at-208-postgres-domain --strict` → `Change 'at-208-postgres-domain' is valid`. El cambio permanece activo porque AT-208 tiene cobertura pendiente.
`uv run --no-sync python scripts/check_secrets.py` → `No potential secrets detected`.
`uv run --no-sync pytest -q` → `61 passed, 1 warning` (deprecación de Starlette/AnyIO).

La migración fue creada con `supabase@3.4.0 migration new at_208_postgres_domain` dentro de un contenedor Node debido a que el CLI local intentó escribir en un home de solo lectura. El fixture `tests/at208/local_auth_fixture.sql` no debe desplegarse: acepta un claim simulado y no valida JWT. La migración requiere los roles y objetos `auth` provistos por Supabase y dos roles dedicados aprovisionados fuera de esta migración: `at208_policy_owner` NOLOGIN NOBYPASS con SELECT acotado y `at208_backend` sin BYPASS ni DML. Los auxiliares de lectura RLS pertenecen al primero; la función de oferta se ejecuta desde el segundo. Antes de aplicarla se debe verificar en un stack Supabase local compatible y luego en el entorno alojado el propietario real del migrador, su pertenencia a los roles, los grants efectivos, la conexión SQL backend y la no exposición del esquema `private`. No se hizo esa verificación ni se aplicó cambio alguno al proyecto alojado.

La función de oferta es una frontera de base de datos, todavía sin ruta FastAPI que demuestre validación de JWT. El `p_actor` solo puede provenir del backend de confianza; una credencial backend comprometida podría atribuir otro actor. No se probó autenticación real, backup administrado de Supabase, carrera simultánea de transferencia, ni despliegue. La prueba secuencial rechaza un destino degradado de editor a viewer, y la función bloquea y comprueba la fila de membresía al transferir. Los auxiliares de mutación aún pertenecen al migrador con BYPASSRLS local; la revisión debe validar su separación en propietarios NOLOGIN de permisos acotados antes de desplegar.

La descripción completa de AT-208 en Linear también exige países, proveedores, sucursales, contactos, clientes, especificaciones y deduplicación de productos, candidatos/selecciones/evaluaciones, servicios y tarifas. Esos modelos están presentes y probados localmente. Las rutas transaccionales de servicio para clientes, tarifas, presupuesto, líneas, entidades, paquetes y snapshots siguen pendientes; candidatura, evaluación y selección tienen funciones SQL locales pero no ruta FastAPI/JWT probada. El snapshot actual solo representa un borrador inmutable; no autoriza emisión. AT-222 define la emisión, y AT-224 la política de cálculo. **AT-208 no cumple Done.**

## Revisión requerida

Antes de integrar, un revisor independiente debe inspeccionar especialmente `SECURITY DEFINER`, el `search_path`, las rutas de idempotencia y auditoría, grants, propiedad residual `BYPASSRLS`, transición de propietario, y la topología SQL en Supabase. El CI ejecuta el mismo script local. La revisión independiente aún no aprobó este diff.
