Fecha: 2026-11-26. Base original: `develop` `c503575e152430908da3f0bb56317867e77d26c9`; se inspeccionó `develop` `846f0e1c2b9eaaee8256794aa5659959b3676022` antes de la corrección. El PR contra `develop` ejecuta CI sobre la combinación actual.

## Ejecución reproducible

Desde la raíz del repositorio, con Docker disponible:

```bash
bash tests/at208/run_local.sh
```

El script crea un contenedor `postgres:17-alpine` sin red ni puerto publicado y lo elimina al terminar. Aplica un fixture local de roles y `auth.uid()` simulado. Primero verifica que la migración falle cerrada si el migrador no pertenece a los roles requeridos; después la aplica con un migrador `NOLOGIN NOBYPASSRLS` y auxiliares de lectura, mutación y auditoría con propietarios separados `NOLOGIN NOBYPASSRLS`. Exporta con `pg_dump -Fc`, restaura con `pg_restore`, comprueba aislamiento y recuentos de datos, y restaura la copia anterior a la migración. La salida observada fue:

```text
AT-208 domain, service and RLS assertions passed
AT-208 trusted rate and budget assertions passed
AT-208 two-session membership/transfer race passed
AT-208 local migration, RLS, backup/restore and baseline rollback passed
```

El test usa cuatro proyectos y cinco usuarios sintéticos. Cubre FKs entre proyectos, catálogo acumulativo, contactos privados, RLS en toda tabla pública, rechazo de DML directo de cliente/backend, valores no finitos, único presupuesto activo, auditoría y fallo cerrado. La admisión rechaza propietarios auxiliares LOGIN y membresía de `authenticated`, `at208_backend` o un LOGIN no confiable antes de crear objetos de dominio. Ejecuta comandos SQL de proyecto/membresía/transferencia, declaración/evidencia/paquete curado, cliente, oferta/tarifa, candidatura/evaluación/selección y presupuesto/línea/borrador. Comprueba idempotencia, revisión esperada, proyección de borrador y evidencia histórica fijada tras cambiar la entidad fuente. Una evaluación adversa supersede una selección activa sin borrarla; otra evaluación en la misma transacción recibe secuencia mayor y permite una nueva selección. La prueba de dos sesiones degrada un editor mientras una transferencia espera el bloqueo del proyecto; luego rechaza la transferencia. La restauración prueba legibilidad y recuentos; no mide RPO/RTO ni sustituye un simulacro alojado.

## Ensayo con imagen oficial Supabase PostgreSQL

La revisión del PR #19 sobre `3d9f35b` identificó dos regresiones P2: reintentos simultáneos de `create_project` y transición con presupuesto inexistente o revisión nula. Se añadió bloqueo transaccional por UUID antes de leer el recibo de creación, y validación explícita de objetivo/revisión antes de mutar o registrar éxito. `tests/at208/concurrent_create.sh` mantiene abierta la primera transacción mientras una segunda llama con los mismos argumentos, y exige un solo proyecto/recibo y el mismo ID. `trusted_budget.sql` exige rechazo de presupuesto ausente con revisión nula o presente, rechazo de revisión nula para un presupuesto existente y ausencia de recibos exitosos. En PostgreSQL descartable local ambas regresiones y el restore pasaron; el workflow ejecuta el mismo script en la imagen oficial fijada. La base vigente inspeccionada fue `develop` `46e97c160963bf094f04d3d9eb4319b61c435441`; el PR debe validar el diff combinado y preservar AT-279.

Se intentó `docker pull ghcr.io/supabase/postgres:17.6.1.102@sha256:90c82488dc721a2b6516c1634b2cc000633f972c4eb6100b68c5aef23ee9e275` (imagen oficial PostgreSQL 17.6.1.102, digest Linux amd64). Los roles mutadores ya no poseen BYPASSRLS en el ensayo local, pero un revisor debe comprobar sus grants, políticas y superficie de funciones antes de integrar.

La descripción completa de AT-208 en Linear exige también revisión e integración. ## Revisión requerida

### Conexión SQL real y límite de Auth (ensayo descartable)

`tests/at208/run_local.sh` crea una contraseña aleatoria en memoria para el contenedor y un LOGIN efímero `at208_login` con `NOINHERIT NOBYPASSRLS`. El servidor exige SCRAM en TCP; no publica puertos ni conecta a redes externas. Tras instalar la migración, concede únicamente la capacidad `SET ROLE at208_backend` a ese LOGIN. Una sesión `psql` autenticada por TCP comprueba `session_user=at208_login`, denegación de un procedimiento sin asumir el rol, `SET LOCAL ROLE at208_backend` dentro de una transacción, creación sintética por `private.create_project`, retorno a `current_user=at208_login` después de `COMMIT` y denegación de `INSERT` directo aun con el rol backend. Se ejecuta el mismo ensayo en la imagen oficial fijada por el job de CI. Resultado local con `postgres:17-alpine`: `AT-208 disposable SCRAM login and effective backend role passed`, seguido de backup/restore verde. Esto prueba la sesión SQL y sus privilegios efectivos, no el aprovisionamiento de roles alojados.

La única ruta HTTP actual de `src/estimate_api/app.py` es `/health`. No hay una operación de dominio que acepte Bearer JWT; por ello **no se verificó Auth/JWT mediante FastAPI**. El fixture SQL `auth.uid()` recibe un claim simulado y cualquier sesión SQL con acceso puede establecer ese GUC; no debe tomarse como autenticación. AT-209 debe implementar una ruta que valide firma, emisor, audiencia y vigencia del JWT de Supabase Auth antes de derivar `p_actor` de `sub`, nunca del cuerpo del cliente; usar una credencial SQL backend privada y la transacción con rol efectivo acotado; y ensayar dos usuarios/proyectos con tokens reales emitidos por Auth local, token ausente/inválido y autorización por recurso. Si el backend elige un pooler, verificar esa misma transacción por su conexión efectiva y modo elegido antes de desplegar. No se ensayó pooler porque este PR no define ni usa uno. No hubo acceso a Auth ni PostgreSQL alojados.

Antes de integrar, un revisor independiente debe inspeccionar `SECURITY DEFINER`, `search_path`, grants/políticas de cada propietario, idempotencia, evidencia fijada, proyección de borrador, bloqueo proyecto→membresía y topología Supabase. El CI ejecuta el mismo script local. La revisión independiente aún no aprobó este diff.
